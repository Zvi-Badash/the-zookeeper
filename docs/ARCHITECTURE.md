# Architecture and interpretation

`ingest.py` streams Parquet record batches, writes original text and scalar fields into a snapshot DuckDB, and stores one normalised float32 vector slot per original row in `vectors.f32`. Row IDs are original row offsets. Normalisation uses float64 norms to avoid overflow; scores use float32 original-space dot products. Unusable rows have explicit reason codes and never enter vector retrieval.

`storage.py` owns a SQLite WAL database for snapshots, durable job outcomes and pair reviews. A single in-process worker serialises import/audit/projection jobs; use one Uvicorn worker. On restart unfinished jobs become interrupted and can be resubmitted; finished caches and reviews survive. No distributed service or custom dataset manifest is involved. Pair review keys sort row IDs and include workflow and snapshot.

`search.py` is shared by leakage, coverage, opposite-label review and atlas neighbours. Every reference scope builds its own persistent index, so a sparse split/label is filtered **before** retrieval. Small populations use exact Faiss flat inner-product search. Auto mode uses IVF-PQ for references above 50,000 rows; it retrieves at least 64 candidates and reranks them from original float32 vectors. Default nprobe=32 is recorded. This remains approximate: reranking does not recover a candidate that was never retrieved. Use the exact sample action before interpreting weak coverage. Explicit approximate mode uses flat search below 1,000 reference rows because PQ training is inappropriate there.

Label review queries each opposite-label reference population, rather than filtering only the overall top neighbour. Self rows are excluded. Reversed pairs are collapsed in the label queue; leakage counts remain unique source rows. Leakage and coverage cache keys include snapshot, scopes, algorithm settings, sampling and code version; thresholds are excluded. Cached match Parquet includes separate `missing_embedding`, `no_match` and `matched` states. Coverage fractions use valid matches as denominator; population, valid-match and missing counts remain visible.

`groups.py` uses SciPy sparse connected components on the cached opposite-label links selected by the cutoff and filters. Group IDs are the minimum member row ID at that cutoff. Groups are candidates linked by scored connections, not all-to-all similarity guarantees; reviews remain attached to canonical pairs. Group members and evidence links are bounded and paginated. Coverage can compute character-length slices independently of supplied size units and shows reference-slice counts, preserving the distinction between population imbalance and embedding-space coverage.

GPU search uses CuPy matrix multiplication over query batches of 64 and reference shards capped at 65,536 vectors and a configurable memory budget. Each shard contributes local top-k scores, then CPU merges the global top-k. It excludes self rows. This path is exact over all eligible references, but has not been benchmarked on the deployment A100. CPU fallback is explicit after a clear capacity/runtime error. CPU flat indexes are in RAM; choose approximate mode for large corpora or provision enough RAM for exact audits. Exact CPU runs currently materialise the scoped reference Faiss index; they do not shard it.

`projections.py` computes incremental PCA on all searchable rows, UMAP on up to 15,000 sampled rows and Barnes–Hut t-SNE on up to 5,000 sampled rows, with deterministic seeds. Each sampled nonlinear fit first reduces to at most 50 PCs. Projection jobs report phases rather than fabricated per-iteration percentages. API responses cap atlas delivery at 30,000 points (UI uses 15,000). Row identity is retained across all views. PCA and nonlinear projections are navigation aids, never audit scores.

`app.py` serves paginated metadata/results and individual source examples. `frontend/src/main.js` owns a shared Monaco viewer used everywhere, local Prettier parser plugins and Plotly. Black uses fixed settings and never reads code-supplied configuration. Dataset code is displayed as literal text; no dataset imports, execution or formatter plugins occur. The viewer initially shows at most 200,000 characters per file, labels partial comparisons, and provides full-open/download. Formatting supports full files up to 2M characters.

## Resource planning

1,500,000 × 4,096 × 4 bytes = 24,576,000,000 bytes = **22.9 GiB** for one dense float32 vector copy. The app retains a slot for unusable rows. The Parquet input is staged as another file; DuckDB stores original source text/metadata. Exact Faiss flat adds another 22.9 GiB for the reference if all rows are indexed, plus IDs, retrieval candidates, filesystem cache, query buffers and Python allocations. IVF-PQ reduces index memory, but training and reranking touch originals and need additional RAM. Scope-specific indexes consume disk; avoid creating many unnecessary scopes. Projection samples materialise bounded high-dimensional matrices (15k × 4096 is ~234 MiB before fit buffers). GPU shards are budgeted independently.

Plan generously (for example 96–128 GiB system RAM and substantial fast SSD capacity for full-size exact work) but treat that as a planning estimate, not a measured minimum. Actual source-code size can dominate disk consumption. Measure wall time, peak RSS, disk high-water mark, page faults and peak VRAM on a representative corpus before committing to full-scale use. No million-row performance claim is made. The optional held-out-train coverage baseline is not included in this release.
